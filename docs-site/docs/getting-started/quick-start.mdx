# Quick start

Two paths: the **core inference API** (one script), then, optionally, the
**curation subsystem** seeded with public sample data.

## 1. Core inference API

```bash
git clone https://github.com/davidamacey/OpenProcessor.git && cd OpenProcessor
./scripts/setup.sh
```

`scripts/setup.sh` pulls the pre-built images, detects your GPU and picks a
profile (`minimal`, `standard`, `full`), writes `.env` from `env.template`
(it never overwrites an existing `.env` unless you pass `--force`),
downloads the base weights, runs the one-time TensorRT export, starts the
core services and runs smoke tests. First run is dominated by TensorRT
compilation (about 30-60 minutes); later starts take seconds.

Useful flags (all from `./scripts/setup.sh --help`):

| Flag | Effect |
|---|---|
| `--yes`, `-y` | Accept defaults, no prompts |
| `--profile=NAME` | Force `minimal`, `standard` or `full` |
| `--gpu=ID` | GPU id to use (default `0`) |
| `--skip-download` / `--skip-export` / `--skip-start` | Skip that step |
| `--force` | Overwrite an existing `.env` |
| `--curation` | Print the curation next steps at the end |

Verify:

```bash
curl http://localhost:4603/health          # readiness: Triton + OpenSearch reachable
curl -X POST http://localhost:4603/detect -F "image=@your-image.jpg"
```

Detection coordinates are normalized to `0.0-1.0`; multiply by the image
width/height for pixels. Day-to-day management:

```bash
./scripts/openprocessor.sh status     # service health
./scripts/openprocessor.sh logs -f    # live logs
make up / make down                   # core stack (Triton + API + OpenSearch)
make up-monitoring                    # core stack + Prometheus/Grafana/Loki/DCGM
```

Prefer to do it by hand? See [Model export](./model-export.mdx) and
[Compose profiles](./compose-profiles.mdx).

## 2. Curation with public sample data

No dataset ships in the repository and nothing proprietary is bundled. The
sample fetchers download small, **license-filtered**, deterministic subsets
of public datasets into the gitignored `data/samples/` directory, from
pinned manifests under `scripts/datasets/manifests/`.

| Make target | What it fetches | Output |
|---|---|---|
| `make sample-coco-readme` | 200 COCO 2017 images, 20 per class (about 1-2 minutes) | `data/samples/coco_va_readme/` |
| `make sample-coco` | 800 COCO 2017 images (10 classes, 80 per class) plus 12-image `upload` and 24-image `post_promote` side sets | `data/samples/coco_va/` |
| `make sample-plates` | 300 Open Images V7 "Vehicle registration plate" images with YOLO-format region labels | `data/samples/oi_plates/` |
| `make sample-clean` | Removes everything under `data/samples/` | |

COCO images are kept only under Attribution, Attribution-ShareAlike, "No
known copyright restrictions" or "United States Government Work" Flickr
licenses; Open Images images only under CC BY 2.0. Each fetch writes an
`ATTRIBUTION.csv` next to the images. Run
`python scripts/datasets/fetch_coco_subset.py --help` or
`python scripts/datasets/fetch_openimages_plates.py --help` for every flag.

### Walkthrough

```bash
# 0. Curation needs the PE-Core encoders (not built by setup.sh)
make export-pe

# 1. Fetch a sample
make sample-coco-readme

# 2. Create only the classes you care about (the registry starts empty)
API=http://localhost:4603
for name in car truck bus motorcycle bicycle; do
  curl -s -X POST "$API/curation/classes" \
    -H 'content-type: application/json' \
    -d "{\"name\": \"$name\", \"group\": \"vehicle\"}"
done

# 3. Configure the ingest detector and narrow it to those classes, and
#    point the source mount at the samples directory
cat >> .env <<'EOF'
OP_INGEST_PRIMARY_DETECTOR_MODEL=yolov11_small_trt_end2end
OP_INGEST_PRIMARY_CLASS_IDS=2,3,5,7
OP_SOURCE_ROOT_HOST=./data/samples
EOF
docker compose up -d --force-recreate yolo-api

# 4. Ingest. --root is a container path under the /data/source mount
docker compose exec yolo-api python scripts/curation/ingest_walker.py \
  --root /data/source/coco_va_readme/images --api-base http://localhost:8000/curation

# 5. Optional: start the async workers and cluster (+ VLM-label) the pool
docker compose --profile curation up -d
curl -s -X POST "$API/curation/pipeline/auto_label/start?run_vlm=true&train_clusters=true"
curl -s "$API/curation/pipeline/auto_label/status"
```

Things that trip people up:

- **`OP_INGEST_PRIMARY_CLASS_IDS`** matters. Without it, a stock detector's
  whole label space (all 80 COCO classes) becomes item proposals.
  `2,3,5,7` is car, motorcycle, bus and truck in COCO's id order.
- **Ingest returns `503`** until `OP_INGEST_PRIMARY_DETECTOR_MODEL` is set
  and that model is loaded in Triton.
- **`OP_SOURCE_ROOT_HOST`** is the host side of a fixed `/data/source`
  mount. The walker's `--root` must be a *container* path under it,
  otherwise every image fails as `unservable_path`.
- **`OP_*` variables are read at import time**: recreate `yolo-api` after
  changing them.
- **`auto_label` clusters only by default** (`run_vlm=false`); the VLM
  labels nothing unless you pass `run_vlm=true` and have a VLM configured
  (see [VLM configuration](../configuration/advanced.mdx#vlm-and-segmenter)).
- `GET /curation/health` reports `degraded` until at least one class
  exists and Triton and OpenSearch are reachable.

### Region sample (`make sample-plates`)

The Open Images set is **region** ground truth (whole frames with a
single region class), not item classes. Import it with
`scripts/curation/import_labeled_dataset.py --images-only` so the labels
never touch the item registry, activate a region profile (see
[Configuration: region detection profile](../configuration/advanced.mdx#region-detection-profile)),
let the detection worker's cascade run, then score it with
`scripts/curation/eval_regions_vs_gt.py`.

Continue with the end-to-end [curation workflow](../operations/curation-workflow.mdx).
