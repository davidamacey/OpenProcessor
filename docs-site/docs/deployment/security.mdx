# Security

:::danger[No authentication]
OpenProcessor's API (port 4603 by default) has **no authentication,
authorization or rate limiting** on any route, core or curation. Run it on
a trusted machine or private network behind your own reverse proxy that
enforces authentication. Never map its ports to a public interface.
:::

This is the deliberate, current state of the project, not a bug.
Optional API authentication is on the [Roadmap](/roadmap).

## Routes that are dangerous without access control

- `DELETE /query/image/{id}` deletes indexed data with no confirmation.
- `DELETE /curation/projects/{project}/models/{model_name}` unloads a
  promoted model from Triton and removes it.
- `DELETE /curation/projects/{project}` deletes a project's indexes and
  files. It needs `?confirm=<slug>` and is refused for the `default` project,
  but there is no authentication behind it.
- `POST /curation/vlm/endpoints` registers a URL the API will send images
  to; see [VLM endpoints](#vlm-endpoints-and-server-side-requests).
- `POST /ingest/directory` reads an arbitrary server-side path: anyone who
  can reach it can make the server read any path it has access to.
- The curation surface adds well over a hundred routes, dozens of them
  writes, under the same no-authentication model.

Curation's own path-taking routes are narrower. Batch ingest and dataset
import resolve image and dataset paths only under the configured source
roots (`OP_SOURCE_ROOT`, `OP_SOURCE_PATH_ALIASES`, the project's upload
root) and fail anything else as `unservable_path` or
`dataset_path_not_allowed`; the `images` routes reject path traversal and
root escapes with a `400`. Dataset archive uploads are extracted with
member-count, size and compression-ratio caps and every extracted path is
checked after symlink resolution.

## Projects are not a security boundary

Projects keep datasets apart so one project's queries and writes can't
reach another's indexes (the OpenSearch client refuses a request that names
an index outside the bound project). They do not add access control: anyone
who can reach the API can read, write and delete any project.

## VLM endpoints and server-side requests

Anyone who can reach the API can register a VLM endpoint URL and make the
API send requests to it. Endpoint URLs are checked before use: this stack's
own services, link-local and cloud-metadata addresses, and anything that
resolves to them are refused, redirects are never followed, and keys are
only ever references (`secret:<slug>`) to files in `./secrets/vlm`, written
on the host with `openprocessor vlm key set <slug>`. An endpoint outside
this deployment needs an explicit acknowledgement; set
`OP_VLM_EXTERNAL_POLICY=deny` to refuse them outright (for air-gapped or
regulated deployments). A URL that resolves to another host on your private
network is still a valid endpoint, so put the API behind your own network
controls. `SECURITY.md` in the repository describes the residual risk.

## LAN access from the one-line installer

:::warning[Cropwright on your LAN]
Cropwright is reachable on your LAN by default, for homelab or small-business use. The API itself stays
bound to 127.0.0.1. On a LAN bind the installer puts a shared HTTP basic-auth login (user `cropwright`) in
front of Cropwright; the generated password is in `secrets/cropwright/password` and is never printed.
Pass `--local-only` to keep everything on 127.0.0.1.
:::

- Basic auth is on by default when Cropwright is published beyond loopback. Set
  `OP_CROPWRIGHT_BASIC_AUTH=false` to skip it (an unattended run reads it from the environment), or change
  the password with `./openprocessor cropwright password` and restart Cropwright. It is plain HTTP, so the
  password is not encrypted on the LAN.
- `--bind <ip>` publishes the API and backend ports on that address, after a warning and a typed `expose`.
  A specific address (for example `--bind 10.0.0.5`) also narrows Cropwright to that interface;
  `--local-only` always wins; `--bind 0.0.0.0` leaves Cropwright on all interfaces. A non-loopback address
  asks you to type `expose` (unattended: `OP_ALLOW_PUBLIC_BIND=1`). A re-run keeps the Cropwright bind you
  chose last time.
- `OP_UI_BIND_ADDRESS` (in `.env`, defaults to `OP_BIND_ADDRESS`) publishes only Grafana, Prometheus,
  OpenSearch Dashboards and MLflow on another address, so LAN browsers can follow resource links while the
  datastore and model APIs stay local. Change `GF_SECURITY_ADMIN_PASSWORD` first; MLflow and Prometheus have
  no auth. `OP_GATEWAY_SUBPATHS=true` (with the `cropwright` profile) instead serves the four monitoring UIs
  under `/grafana/`, `/prometheus/`, `/dashboards/` and `/mlflow/` on Cropwright's one port, so they can stay
  on loopback; it needs a non-default `GF_SECURITY_ADMIN_PASSWORD`.
- Cropwright's nginx reaches the API over the Docker network, so LAN browsers never need the API port. The
  UI can reach every route above: use it only on a network you trust, never port-forward any OpenProcessor
  port to the public internet, and put a reverse proxy with authentication in front for anything wider.

Release checksums (`SHA256SUMS`, `images.lock`) prove integrity, not authenticity: they come from the same
origin as the files they cover.

## Other default-open components

- **Grafana** (monitoring profile) ships with `admin` / `admin`. Change
  it before anyone else can reach it.
- **OpenSearch** and **OpenSearch Dashboards** run with the security
  plugin disabled (a development default). Enable it before any
  production or multi-tenant deployment.
- **`alloy`** (monitoring profile) mounts the Docker socket to tail every
  container's logs.

## The Docker socket overlay

`docker-compose.gpu-arbiter.yml` mounts `/var/run/docker.sock` into
`api` so training jobs can stop and restart named containers around a
run (`OP_GPU_ARBITER_CONTAINERS`). Mounting the socket gives that
container's processes **root-equivalent control of the whole Docker
host**, not just this project. Only enable it on a host where you trust
the API's full dependency stack. Without the overlay, arbiter calls are
no-ops and the API logs one `arbiter_docker_unavailable` warning per
outage, and trainer reachability is still checked through the trainer's
heartbeat file.

## Reporting a vulnerability

For an issue that is **not** one of the known gaps above, use GitHub's
private vulnerability reporting on the
[repository](https://github.com/davidamacey/OpenProcessor/security)
rather than a public issue. Include reproduction steps, the affected
version or commit, and your assessment of impact. Security fixes land on
`main`; use the latest tagged release.
