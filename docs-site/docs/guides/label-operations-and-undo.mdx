# Label operations and undo

A label or move, single or bulk, is recorded as a **label operation**. List recent ones and undo any of
them from the server, item by item, long after the browser tab that made it is gone. Undo
never reverts a later human edit. Examples assume `API=http://localhost:4603` and project
`cars`.

## What is recorded

`PUT .../crops/batch_label` and `POST .../crops/move` (with `crop_ids` or a `selection`) each
create one operation; the response carries its `op_id` (null for an empty selection or a dry
run). `PUT .../crops/{crop_id}/label` does too: it stays a synchronous write, records its
operation (one member) in the same request and answers `op_id`, so one Z, or the Label history
after a reload, undoes it the same way. Each written item is tagged with `label_op_id`, and its class history entry carries the
same `op_id`.

- Records are PostgreSQL rows (an operation plus a member row per item written), written before
  the first item. The newest 200 per project are kept; one being written or undone is never
  pruned.
- A crash while writing leaves `interrupted`, while undoing `undo_interrupted`; both can be
  undone again.
- Operations name the class they wrote, never a class id.

## List operations

```bash
curl -s "$API/curation/projects/cars/label_ops?limit=20&undoable=true"
curl -s "$API/curation/projects/cars/label_ops?limit=50&after=$NEXT"   # older page
```

Newest first (`limit` 1 to 50, default 20; `undoable=true` keeps only undoable ones). Per
operation: `kind` (`label` or `move`), `class_name`, `selected`, `count`, `conflicts`,
`current` (items still carrying this label), `status`, `undone`, `undoable`, `last_undo`. An
operation is undoable while `current` is above zero and it is not being written or undone.
`next_after` is the last `op_id` of the page while older ones exist, else `null`; pass it as
`after` (a malformed value is `422 invalid_request`).

## Undo (dry run first)

```bash
curl -s -X POST "$API/curation/projects/cars/label_ops/$OP/undo" \
  -H 'Content-Type: application/json' -d '{}'                  # dry run, writes nothing
curl -s -X POST "$API/curation/projects/cars/label_ops/$OP/undo" \
  -H 'Content-Type: application/json' -d '{"dry_run": false}'
```

One outcome is decided per item, again inside the write, so a person's edit that races the
undo wins:

| Outcome | Meaning | Written |
|---|---|---|
| `restored` | Still carries this operation's label, unchanged since | the class state from before, exactly |
| `already_undone` | This operation's write on the item was already undone | nothing |
| `kept_changed` | A person or import relabelled it, a later operation wrote it, it was excluded, its class was merged, or it was deleted | nothing |
| `kept_holdout` | In the frozen test holdout | nothing |
| `kept_stale_class` | The class to restore was renamed, merged or deleted | nothing |

`matched` is the sum of these five plus `conflicts` (conditional writes that lost a race; ids
in `conflict_ids`).

- Undo is per item: an operation with some edited items is still undoable for the rest.
- Operations can be undone in any order. If B relabelled part of A, undoing A keeps those
  items; undoing B puts them back under A.
- A bulk undo never touches the test holdout; a single item can still be undone with the
  per-item route. Undoing a label also restores the accuracy-audit verdict.
- The pass runs inside the request in pages of 500 items, with no cap on item count (20,000
  items took about 20 to 26 s on a busy host).

Errors: `404 label_op_not_found` (unknown, malformed or pruned), `409 already_undone`,
`409 label_op_busy` (another undo of this project is running), `409 label_op_in_progress`
(still being written).

## Per-item and small-batch undo

`POST .../crops/label/undo_batch` takes up to 5,000 crop ids and undoes the next step of
each. To undo a whole bulk label or move, use the operation route. Region edits have their own
undo ([Multi-box regions](./multi-box-regions.mdx#undo)).

## In Cropwright

The **Label history** tab of the Quality page lists the recorded operations (single and bulk) and shows the
server's dry run before an undo. Semantics:
[`docs/design/cq3_label_operations.md`](https://github.com/davidamacey/OpenProcessor/blob/main/docs/design/cq3_label_operations.md).
