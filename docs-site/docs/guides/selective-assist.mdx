# Selective VLM and segmenter assist

Ingest, cluster, name a few clusters by hand, then ask the VLM (and the segmenter) for help
on exactly the part you are working on: one cluster, selected crops, one crop or one box.
Nothing is called until you start a run.

An **assist run** is one request shape for every scope. It plans first (dry run is the
default) and shows what it would do. Its output is suggestions: a class, the attributes the
prompt pack declares, box verdicts and, for a cluster, a proposed label. A suggestion never
overwrites a label a human or an import set. Routes and fields:
`docs/design/curation_api_contract.md`.

`API=http://localhost:4603/curation/projects/cars` is assumed.

## The recipe

1. **Ingest** with the VLM off. A project calls no VLM until it activates one or a run names
   one ([Pipeline modes](./pipeline-modes.mdx)).
2. **Cluster:** `POST $API/pipeline/auto_label/start?train_clusters=true`. If a cluster mixes
   things, run a finer cluster profile (`POST $API/clusters/runs`) and activate the new
   partition. List a cluster's members with `GET $API/crops?cluster_uid=<cluster uid>`.
3. **Name some clusters by hand** in Cropwright or with `PUT $API/crops/batch_label`. Those
   labels are human-validated; no automated writer overwrites them.
4. **Assist** on a cluster, selection, crop or box: pick what the VLM sees, what to do and
   which VLM; read the plan; start the run. The Workspace's AI menu starts it on the selection
   or the scope.
5. **Read the proposal and apply it on purpose.**

In Cropwright, steps 4 and 5 are the **Assist…** button on a cluster page
([Assist in Cropwright](../cropwright/user-guide/assist.md)).

## What the VLM sees: the sample

| Choice | When | Request |
|---|---|---|
| Selected crops (one crop is a selection of one) | You know which to ask about | `target` `{"kind":"crops","crop_ids":[...]}`, `sample.mode` `all` |
| Every member of a cluster or filter | Small scope, or an answer for each | `target` `{"kind":"cluster","cluster_uid":"..."}`, `sample.mode` `all` |
| A random representative sample | Large scope; you want a label for it, not an answer per member | `sample` `{"mode":"representative"}` |

A representative sample is seeded (same scope, seed and size give the same members). Default
size is `max(8, min(64, ceil(2 * sqrt(n))))` for `n` members (5 sends all, 25 sends 10, 100
sends 20, 1000+ sends 64); `sample.size` (at most 256) overrides it. The plan reports
`scope_count`, `sampled`, the strata and `estimated_vlm_calls` before you start.

```bash
curl -s -X POST "$API/assist/runs" -H 'content-type: application/json' -d '{
  "target": {"kind":"cluster","cluster_uid":"7c1e0a52-3b64-4f0e-9d58-2a1f6b3c9e10"},
  "sample": {"mode":"representative","size":24,"seed":3},
  "actions": ["classify","attributes"]
}'
```

The frozen test holdout and ignored items are never sent. A locked item (class set by a human
or import, or validated) is sent for a suggestion and counts as a vote, a useful check on your
own label; its class is never written. A scope over 5000 items with `sample.mode` `all` is
`422 assist_too_large`: sample it, narrow it, or use the
[auto-label job](./pipeline-modes.mdx#c-vlm-assisted-labeling-of-a-large-batch).

## What to do: the actions

| Action | Targets | Result |
|---|---|---|
| `classify` | crops, cluster, filter | A class suggestion per sampled item via the guarded VLM writer; a locked, validated or held-out item keeps its class and gets the answer as a suggestion only |
| `attributes` | crops, boxes, cluster, filter | The attributes the prompt pack declares, stored apart from labels |
| `verify` | crops, boxes | The VLM judges each box still open to a machine verdict; human- and import-owned boxes are never sent |
| `segment` | crops, cluster, filter | Re-queues the items for the segmenter in the region worker ([below](#segmenter-verification)) |

A run takes the VLM and pack by name: `"vlm": "env"`, `"prompt_pack": "cars"` (`name` or
`name@revision`). Omitted, it uses the project's active endpoint and default pack. An
endpoint outside the deployment needs `"acknowledge_external": true`. The run pins what it
resolved, so the result says what produced it.

## Attributes in prompt packs

A [prompt pack](./prompt-packs.mdx) declares the facts it wants reported:

```json
{"attributes": [
  {"key": "make", "description": "The maker of the car", "applies_to": "item"},
  {"key": "body_style", "description": "The body style", "values": ["sedan", "suv", "pickup"], "applies_to": "item"},
  {"key": "rim_material", "description": "What the rim is made of", "applies_to": "box"}]}
```

`examples/prompt_packs/vehicle_wheel.json` is a complete pack; `general_objects.json` is a
domain-neutral one (`brand` free text, `colour` and `material` closed lists). The VLM answers
each attribute with a value and a confidence (`high`, `medium`, `low`); undeclared keys and
values outside a closed list are dropped and counted as `invalid_values`. Attributes are
stored in the item's `assist` object (box attributes under `assist.boxes`), never in the
class or box, and Cropwright shows them as dashed "VLM suggests" chips. Preview on up to 64
crops with [Test on a crop](./test-on-crop.mdx).

## The proposal for a cluster

A `classify` run over a cluster reads the sampled answers as a label for the scope: the top
class, the **agreement** (share of answers for it), the vote distribution, new-class names
the VLM proposed when nothing fit, and an attribute summary. It names a class only when at
least 3 answers exist and agreement reaches `min_agreement` (default 0.6, accepts 0.5 to 1.0;
the Cropwright **Agreement needed** field); otherwise only the distribution is shown.

Applying is a separate call, with a dry-run count first:

```bash
curl -s -X POST "$API/assist/runs/RUN_ID/apply" -H 'content-type: application/json' \
  -d '{"class_name":"spoiler","dry_run":true}'
```

The count is the members it would label; locked, validated, held-out and ignored members are
left alone. `"dry_run": false` labels them as a human would (validated, trainable). A run
remembers the members it resolved; if a new partition is activated or members move,
`scope_now.changed` turns true and apply refuses with `409 scope_changed` until you run
again. The class is matched by name; a name the registry lacks is `409 class_not_in_registry`
(create the class first).

## Segmenter verification

The segmenter proposes boxes from a text prompt; the VLM can verify each one. That check is a
choice:

- **Per project:** the VLM policy's `region_verify` is `vlm` (default: the region worker asks
  the project's VLM when it has one) or `none` (accept boxes without a VLM). Cropwright has it
  on the VLM scope panel in Settings.
- **Per run:** the `segment` action re-segments chosen crops, a cluster or a filter, and
  `segment` `{"verify": "vlm" | "none"}` says how the worker verifies those items only. The
  run waits in `waiting_region` until the boxes are written, then completes with the `segment`
  counts. A validated region set is skipped.
- **Segment, then verify with a chosen VLM:** the region worker verifies with the project's
  active VLM only. To judge the new boxes with another endpoint, send `segment` with
  `verify` `none` plus the `verify` action in one request, on a `crops` target, with `vlm`
  naming the endpoint:

```bash
curl -s -X POST "$API/assist/runs" -H 'content-type: application/json' -d '{
  "target": {"kind":"crops","crop_ids":["050ad3a2...","05ad8ec2...","0a1f9c3e..."]},
  "actions": ["segment","verify"],
  "segment": {"verify":"none"},
  "vlm": "env",
  "dry_run": false
}'
```

Segment refusals: `409 region_profile_required`, `no_segmenter_leg` (no
`segmenter_text_prompt`), `region_stage_paused`, `verify_endpoint_mismatch` (`verify` `vlm`
with an endpoint other than the project's). See [Region profiles](./region-profiles.mdx) and
[wheels on cars](./wheel-example.mdx).
