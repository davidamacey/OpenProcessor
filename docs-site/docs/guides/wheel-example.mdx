# Worked example: wheels on cars

The whole pipeline on public data. The primary detector finds cars in COCO photos (CC BY);
the region stage then finds each wheel on each car. COCO has no wheel labels, so the output
is machine-proposed wheel boxes a person reviews. Everything needed ships in the repository.

## What each file does

| File | Role |
|---|---|
| `examples/region_profiles/vehicle_wheel.json` | Region profile: the segmenter is prompted with `wheel` inside items whose class name is `car` (`parent_classes`). No detector leg until you train and promote one. `max_regions_per_item` 4, `text_reader` `none`, `region_class_name` `wheel`, display names `Wheels` / `Wheel` |
| `examples/prompt_packs/vehicle_wheel.json` | Prompt pack: classify a car crop and verify each numbered candidate box as a wheel (tire plus rim); names the per-box reply keys a multi-box profile needs; reads no text |
| `examples/bakeoff/vehicle_wheel/profile.json` | Bake-off profile for wheel detectors you train later (`class_names` `["wheel"]`, COCO car class as context; set `triton_model` to your promoted detector) |
| `scripts/examples/wheel_example_live.py` | Runs the steps below against a live stack |
| `tests/integration/test_wheel_example_e2e.py` | The same walk offline with fakes at the OpenSearch, Triton, segmenter and VLM boundaries |
| `make sample-coco-cars` | Fetches the 60 car photos |

The profile selects items by class **name** (`parent_classes` matches an item's `class_name`
or the detector's own label); a raw class index is never used.

## Prerequisites

- Core stack and `curation` workers up, PE encoders built, a primary detector loaded in Triton
  (a stock COCO YOLO is enough). See [Quick start](../getting-started/quick-start.mdx).
- The segmenter service running (`OP_SEGMENTER_URL`).
- A VLM endpoint registered and activated for the project, unless you accept unverified
  segmenter boxes ([VLM selection](./vlm-selection.mdx)).
- The image folder mounted read-only at the same path in `api` and the detection worker
  (`OP_SOURCE_ROOT_HOST` at `/data/source`). If only the API has it, ingest succeeds but every
  later worker read fails.

## Run it with the script

```bash
make sample-coco-cars      # 60 CC BY car images into data/samples/coco_car
.venv/bin/python scripts/examples/wheel_example_live.py \
    --api http://localhost:4603 --project wheels \
    --container-dir /data/source/coco_car/images
```

`--container-dir` is the folder as the API container sees it; for example set
`OP_SOURCE_ROOT_HOST=./data/samples` so `data/samples/coco_car/images` appears as
`/data/source/coco_car/images`. `--host-dir` (default `data/samples/coco_car/images`) is where
the script lists files on the host. Other flags: `--api-prefix` (`/curation`),
`--drain-timeout` (seconds, 1800).

The script: creates project `wheels` and classes `car` and `wheel`; saves the example profile
and pack as `wheel_example` and activates both; ingests in batches of 16; polls the region
queue until drained; exports the wheel boxes cropped to their car.

## The same steps by hand

```bash
API=http://localhost:4603/curation/projects/wheels
curl -s -X POST http://localhost:4603/curation/projects \
  -H 'Content-Type: application/json' -d '{"slug": "wheels", "display_name": "Wheels"}'
for name in car wheel; do
  curl -s -X POST "$API/classes" -H 'Content-Type: application/json' -d "{\"name\": \"$name\"}"
done

BODY=$(jq '{name: "wheel_example", body: del(._comment, .name)}' examples/region_profiles/vehicle_wheel.json)
curl -s -X POST "$API/region_profiles" -H 'Content-Type: application/json' -d "$BODY"
curl -s -X POST "$API/region_profiles/wheel_example/activate" \
  -H 'Content-Type: application/json' -d '{"expected_active": null}'

BODY=$(jq '{name: "wheel_example", body: del(._comment, .name)}' examples/prompt_packs/vehicle_wheel.json)
curl -s -X POST "$API/prompt_packs" -H 'Content-Type: application/json' -d "$BODY"
curl -s -X POST "$API/prompt_packs/wheel_example/activate" \
  -H 'Content-Type: application/json' -d '{"expected_active": null}'

curl -s -X POST "$API/ingest/batch" -H 'Content-Type: application/json' \
  -d '{"items": [{"path": "/data/source/coco_car/images/IMAGE.jpg", "source": "coco_car"}]}'
curl -s "$API/ingest/region_drain"
curl -s -X POST "$API/export/single_class" -H 'Content-Type: application/json' \
  -d '{"profile_name": "wheels", "box_source": "region", "region_class_name": "wheel",
       "image_mode": "item_crop", "class_ids": []}'
```

The `jq` drops `_comment` and `name`, which are not part of the body. Activation fails with
422 if the pack and profile do not pair (the profile allows 4 boxes, so the pack must name the
per-box reply keys; the example does). Validate drafts first with
`POST .../region_profiles/validate` and `POST .../prompt_packs/validate`
([Region profiles](./region-profiles.mdx), [Prompt packs](./prompt-packs.mdx)).

`GET .../ingest/region_drain` returns `drained`, `pending_detection`, `pending_verification`,
`total_unfinished`, `stable_for_s` and `stall_reason`; repeat until `drained` is true. To try
the profile on one stored crop first: [Test on a crop](./test-on-crop.mdx).

To re-segment three crops and verify the new boxes with the run's own VLM (the run is
`waiting_region` while the region worker segments):

```bash
curl -s -X POST "$API/assist/runs" -H 'Content-Type: application/json' \
  -d '{"target": {"kind": "crops", "crop_ids": ["car_1", "car_2", "car_3"]},
       "actions": ["segment", "verify"], "segment": {"verify": "none"}, "dry_run": false}'
```

## What you should see

- Items proposed as `car` carry up to four wheel boxes in `region_boxes`, each with its own
  `state`, `score` and `detector`. With a VLM a verified box is `accepted`, a wrong one
  `rejected` ([Multi-box regions](./multi-box-regions.mdx)). Wheel boxes have no text fields.
- The export answers with `export_dir`, `positive_images`, `split_counts` and the integrity
  envelope. Positives are accepted wheel boxes cropped to their car (`item_crop`); rejected
  boxes are not exported; boxes a person marked as false positives become hard negatives.
- The boxes are for review: confirm, move, add or reject them, then export again.

Offline version (no GPU or stack): it creates the project through the lifecycle route,
imports a small fixture, runs the region worker against the example profile, exports, and
asserts at every step that a sibling project is untouched and class identity is the name:

```bash
.venv/bin/python -m pytest tests/integration/test_wheel_example_e2e.py -v
```
