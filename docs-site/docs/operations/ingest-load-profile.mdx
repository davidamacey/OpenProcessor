# Ingest load profile and GPU memory

Photo ingest calls three Triton models: the detector, the PE image encoder and (for text
search) the PE text tower. By default Triton also preloads the face, MobileCLIP and OCR models.
On a 48 GB card they take 27.7 GB, and the frame engine (the GPU decode, about 6 GB at its
working sizes: its shared-memory region, its memory pool cap and the CUDA context) shares the
card with them.

## What each model costs

Measured on an RTX A6000 (GPU memory after loading each model on top of the ingest profile's
8.8 GB; unloading returned every byte):

| Model | Used by | GPU memory |
|---|---|---|
| `scrfd_10g_bnkps` | `/faces/*`, `/analyze`, core `/ingest`, `/search/face` | 6,846 MiB |
| `arcface_w600k_r50` | same as above | 2,754 MiB |
| `mobileclip2_s2_image_encoder` | `/embed/image`, `/embed/batch`, `/embed/boxes`, `/search/image`, `/search/object`, `/analyze`, core `/ingest` | 3,454 MiB |
| `mobileclip2_s2_text_encoder` | `/embed/text`, `/search/text` | 1,430 MiB |
| `paddleocr_det_trt` | `/ocr/*`, `/search/ocr`, `/analyze`, curation text reading | 1,642 MiB |
| `paddleocr_rec_trt` | same as above | 11,572 MiB |
| `ocr_pipeline` (calls the two OCR models) | `/ocr/*` | 0 MiB (the two above load with it) |
| Total | | 27,698 MiB |

The detector, `pe_image_encoder` and `pe_text_encoder` (curation ingest, search and clustering)
are the same in both profiles, and the frame engine runs in both. Face and OCR models are loaded on the first
call under the ingest profile, so those calls pay a few seconds once.

## What happens when the card is short of memory

The frame engine keeps a byte budget (`OP_FRAME_ENGINE_BUDGET_MIB`, default 2048). A photo
reserves its decoded frame from it before decoding and waits its turn (at most
`OP_FRAME_ENGINE_BUDGET_WAIT_SECONDS`, default 4) instead of failing a CUDA allocation. The
budget is reserved when the engine starts: an engine that cannot hold it does not start and
ingest decodes on the CPU; the route counters (`op_decode_route_total`) show it. A wait that
times out is an overload answer: the API retries it three times and then decodes the photo on
the CPU as `cpu_gpu_memory`. A photo that still hits a failed allocation or is larger than the
budget is answered with a status and decoded on the CPU, counted in `op_decode_route_total` as
`cpu_gpu_memory` or `cpu_over_budget`. The stage counter
`op_frame_engine_stage_seconds_total{stage="budget"}` is the time spent waiting, and
`op_frame_engine_overloads_total` counts the overload answers.

A non-zero `cpu_gpu_memory` rate means the card is too full: use the profile below or unload
models you do not use.

## The opt-in profile

```bash
# in .env
OP_LOAD_PROFILE=ingest
./openprocessor restart
```

The CLI then adds `docker-compose.ingest-focus.yml`, which preloads only the detector and the
PE models. With plain Compose add `-f docker-compose.ingest-focus.yml` yourself. The default
(`OP_LOAD_PROFILE=full`) is unchanged.

Every other endpoint still answers. The first call that needs a model Triton does not hold
(`/faces`, `/embed`, `/search`, `/ocr`, `/analyze`, the core `/ingest`, and curation text reading)
makes the API ask Triton to load it, which takes a few seconds once; the model then stays
resident. If the card cannot hold it the call fails with Triton's error. Loading a model back
into a card that ingest filled can fail: keep the default if you use those endpoints
regularly.
