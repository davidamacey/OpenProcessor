# Ingest stage timing

`gpu_image_prep` is the Triton model that decodes a photo on the GPU, runs the
detector, builds the crop and frame squares for the embedding model, and
encodes the crop JPEGs. Stage timing says where the time of one image goes
inside it, so a throughput change can be attributed to a stage rather than
guessed.

The counters follow three rules that Triton 2.70 (26.06) needs (issue
[#390](https://github.com/davidamacey/OpenProcessor/issues/390)): keep the metric families alive,
drop series before families, increment from one thread. Follow the same rules if you add custom
metrics to another Python-backend model.

## The counters

Two Triton counters, both labelled `stage`, on Triton's metrics port (4602 in
the default compose file, the `triton` job in Prometheus):

| Series | Meaning |
|---|---|
| `op_gpu_prep_stage_seconds{stage}` | Summed host wall seconds spent in the stage |
| `op_gpu_prep_stage_observations{stage}` | Images that ran the stage |

Seconds divided by observations is the mean per image. Stage seconds are sums
over concurrent requests: compare them across runs and shares, never add them
up to wall time. The model is loaded on first use, so the series appear after
the first image.

| Stage | What it covers |
|---|---|
| `queue` | Wait for a free slot and a worker thread |
| `decode` | Header routing, nvJPEG decode, EXIF orientation |
| `letterbox` | Detector letterbox canvas |
| `detect` | Detector call and box decoding |
| `embed_frame` | Whole-frame square for the embedding model |
| `embed_crops` | One square per detection (or stored box) |
| `embed_pe` | The embedding model calls over those squares |
| `crop_copy` | Device-to-host copy of each detection's pixels |
| `crop_jpeg` | JPEG encode, summed over the image's crops (host threads) |
| `blur` | Laplacian sums of the frame and every detection |

Stored-box mode (the embed reprocess pass) and the CPU-decode fallback publish
only the stages they ran.

### Asynchronous kernels and `STAGE_SYNC`

CUDA launches return early, so by default a kernel stage (`letterbox`,
`embed_frame`, `embed_crops`, `blur`) ends when its launches are queued, and
its GPU time lands in the next stage that waits (usually `detect` or
`embed_pe`). The model parameter `STAGE_SYNC` (default `"0"` in
`models/gpu_image_prep/config.pbtxt`) set to `"1"` waits for the stream at the
end of those four stages so the time is attributed where the work ran. That
removes the overlap inside one image, so a `STAGE_SYNC=1` run is attribution
only, never a throughput number. Keep such runs in separate rows.

## Reading them in Prometheus and Grafana

Prometheus already scrapes Triton's metrics port when the `monitoring` profile
is up (see [Monitoring](./monitoring.mdx)). Mean milliseconds per image by
stage over five minutes:

```promql
1000 * rate(op_gpu_prep_stage_seconds[5m]) / rate(op_gpu_prep_stage_observations[5m])
```

Depending on the exporter version the series may carry a `_total` suffix; the
profile tooling accepts both. The shipped Grafana dashboards do not have a
`gpu_image_prep` panel yet, so use the Explore view or add one. The existing
`op_pipeline_stage_seconds_*` series (Ingest pipeline dashboard) are the API
side of the same ingest; read both together.

How to read the result: the stage with the largest share of summed seconds is
where an image spends its time, not necessarily what limits throughput. A
large `queue` share means requests wait for the model's worker slots. If
`decode` or `crop_jpeg` dominate, the work is host CPU. If the launch stages
(`letterbox`, `embed_crops`, `crop_copy`) grow with the number of batches in
flight for the same work, suspect host-side launch and thread contention
rather than GPU kernels, and confirm with a `STAGE_SYNC=1` run at one batch at a time.

## Profiling a run

Two scripts under `scripts/bench/`, run from a checkout against a running
stack:

- `run_baseline.py` ingests a manifest of images into fresh projects and
  writes a JSON and markdown report. `--reps N` repeats in a fresh project
  each time, `--drop-cache` drops the manifest files from the page cache
  before each repetition, and the report records the host load average
  (`noisy` when the 1-minute load at the start is above 16), a GPU
  utilisation median and a `gpu_prep_stages` block (seconds, images, mean and
  share per stage, from the Triton counter delta; needs
  `--triton-metrics-url`). `--clients N` posts N batches at once (one batch at a time leaves
  the API under-driven; use 4 for throughput).
- `ingest_profile.py` wraps it with the fixed measurement protocol (3
  repetitions, cache dropped, GPU sampled every 0.5 s, policy `all`, stage
  `ingest`) and adds the API container's CPU seconds and the Triton
  container's CPU.

```bash
.venv/bin/python scripts/bench/ingest_profile.py run setB MANIFEST \
  --api-url http://127.0.0.1:4603 \
  --triton-metrics-url http://127.0.0.1:4602/metrics \
  --path-map HOST_DIR=CONTAINER_DIR \
  --api-container NAME --triton-container NAME \
  --out-root artifacts_local/bench/v070/sp0

.venv/bin/python scripts/bench/ingest_profile.py table \
  setA=artifacts_local/bench/v070/sp0/setA setB=artifacts_local/bench/v070/sp0/setB
```

`table` prints one block per row: median images per second (with range), GPU
and CPU use, the API's pipeline stages, Triton queue and compute times, and
the `gpu_image_prep` stages with mean milliseconds per image and share. It
holds aggregates only. A row that was `noisy` is an upper bound on time and a
lower bound on throughput; repeat it on a quiet host before quoting it.
`scripts/bench/sample_copy.py` makes a seeded, checksummed NVMe copy of a
photo sample under neutral names, so a private set never has its path in a
report.

Run with the stack's real GPU, and never on a card another job is using.

## What was measured, and what it meant

Throughput on one RTX A6000 with a private set of 3,000 photos of about 21 MP (ratios, not public
data), 3 repetitions, host load 13 to 35. Raw rows are in `docs/benchmarks/v070/spf/`; the table and
method are in the SPF section of
[`v070_measurement_log.md`](https://github.com/davidamacey/OpenProcessor/blob/main/docs/research/v070_measurement_log.md)
and in [`PERFORMANCE.md`](https://github.com/davidamacey/OpenProcessor/blob/main/docs/PERFORMANCE.md).

| Stack | Instances | 4 batches at once | GPU | Fallbacks |
|---|---|---|---|---|
| Ingest load profile | 2 | 48.3 img/s | 94 % | 0 |
| Default load list | 1 | 38.9 img/s | 83 % | 0 |
| Default load list | 2 | 35.9 img/s | 72 % | 0.6 to 5.6 % (card full) |
| Ingest load profile, card limited to 24 GiB | 1 | 38.1 img/s | 84 % | 0 |

Earlier findings from the same campaign: the source device does not matter, ingest saturates from
about 8 concurrent requests, and a second `gpu_image_prep` instance raised ingest by about 51 percent
only while the card had room for it. With every default model loaded two instances do not fit, so the
`full` profile runs one instance. The stage counters showed that the fall in throughput past four
batches was device-memory exhaustion (photos falling back to the CPU decode), not CUDA-call overhead
(issue [#392](https://github.com/davidamacey/OpenProcessor/issues/392)).

How to choose between the profiles, and what each model costs in GPU memory, is in
[Ingest load profile and GPU memory](./ingest-load-profile.mdx).
