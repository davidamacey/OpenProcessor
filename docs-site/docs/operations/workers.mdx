# Workers and heartbeats

Browse, label and export work with no workers. Workers run every job (a row in
PostgreSQL, picked up through Valkey) and keep datasets moving. They use the
same `openprocessor` image as the API.

One set of workers serves every project. A job names its project; the stream
workers visit each active project in turn, skip paused ones and bind a project
only around its own work. The detection worker splits each fetch round-robin
between projects and caps in-flight items per project. Replicas of a stream
worker share projects through leases in PostgreSQL.

```bash
./openprocessor curation up                    # or: make curation-up
make curation-status                           # which worker containers are up
make curation-logs                             # follow all worker logs
make curation-down
```

## The always-on workers

These start with the core stack.

| Service | Queue | What it does |
|---|---|---|
| `jobs-worker` | `jobs` | Runs most jobs: label operations, dataset import, bulk ingest, reprocess, scores, promote, combine, project create and delete, embedding builds, near-duplicate runs. Concurrency `OP_JOBS_CONCURRENCY` (default 4); replicas `OP_JOBS_REPLICAS` |
| `periodic-worker` | `periodic` | Runs the scheduled ticks and the reaper |
| `open-vocab-worker` | `open_vocab` | The open-vocabulary sweep |
| `jobs-beat` | | The beat scheduler: one replica. It queues the reaper (every 30 s), the ingest dispatcher, the open-vocabulary sweep, the serving inventory, the near-duplicate rescore, the cluster refresh, the optional database backup and the GPU arbiter tick |

The **reaper** recovers a job whose worker died (it becomes `interrupted`, and
resumes by itself when the job kind allows), fails the jobs of a queue whose
worker profile never started, and prunes old events and finished jobs.

## The curation profile

| Service | Entrypoint | What it does |
|---|---|---|
| `curation-detection-worker` | `python -m scripts.curation.worker --continuous` | Pulls `pending_detection` / `pending_verification` items and runs each project's active region profile's cascade: detector, optional segmenter leg, VLM verification, per-box text reading. Idles for a project with no active profile. Follows a project's config at quiesce points: a newly activated profile, prompt pack or VLM endpoint takes effect once the queues drain. |
| `curation-vlm-worker` | `python -m scripts.curation.vlm_worker --continuous` | Continuously asks each project's active VLM for class suggestions on unvalidated items that have a vector in the primary item space, on its own schedule. |
| `curation-auto-label-worker` | queue `autolabel` | Runs the jobs queued by `POST /curation/projects/{project}/pipeline/auto_label/start`, one at a time: embedding of missing vectors, and VLM labeling only when the job says `run_vlm=true`. |
| `curation-assist-loop-worker` | queue `assist_loop` | Runs auto-label loops queued by `POST /curation/projects/{project}/assist/loops`, in time slices, with the project bound. It builds its own VLM labelers, so it needs the source-image, `./data` and `./secrets/vlm` mounts that `curation-auto-label-worker` has. A loop it was running when it died reads `interrupted` until resumed. While a loop is live the cluster refresh is held. See [Auto-label loop](../guides/auto-label-loop.mdx). |
| `cluster-worker` | queue `cluster` | Runs clustering runs and the periodic cluster refresh, one task per child process so its memory returns to the system. |

The bake-off evaluator (`curation-evaluator`, queue `gpu_eval`), the trainer
(`curation-trainer`, `gpu_train`) and the model-export worker
(`model-export-worker`, `gpu_export`) have their own profiles and need a GPU
of their own; `openprocessor curation up curation-evaluator` starts the
evaluator on purpose.

`api`, `curation-detection-worker`, `curation-auto-label-worker`,
`curation-assist-loop-worker` and `jobs-worker` must mount the same source
directory (`OP_SOURCE_ROOT_HOST` to `/data/source`, read-only), or that worker's
reads fail with `detection_failed` / `image_unavailable`. After changing it, run
`./openprocessor start`.
Details: [Basic configuration](../configuration/basic.mdx) and
[Ingest a large folder](../guides/ingest-large-folder.mdx).

## Which worker needs what

| Worker | Needs Triton | Needs a VLM | Needs a GPU of its own |
|---|---|---|---|
| `curation-detection-worker` | Yes (`depends_on: triton-server`), for the region detector | Only if the region profile uses VLM verification | No |
| `curation-vlm-worker` | No | Yes. It idles when the project has no VLM. | No |
| `curation-auto-label-worker` | Only for `embed_missing=true` jobs, which call the PE encoder on `triton-server` | Only for jobs with `run_vlm=true` | No |
| `cluster-worker` | No | No | No (the opt-in `docker-compose.gpu-clustering.yml` gives one to `curation-auto-label-worker`) |
| `curation-evaluator` | No | No | Yes (`EVALUATOR_GPU_ID`) |

The detection worker verifies regions; the VLM worker suggests classes. A project
whose VLM is off does neither.

## Which workers to run

[Pipeline modes](../guides/pipeline-modes.mdx) says which to start. Stop automatic
clustering per project with the ingest policy field `clustering.automatic=false`, or
for all with `OP_CLUSTER_REFRESH_INTERVAL_S=0`.

## Heartbeats instead of `pgrep`

The two stream workers write `{ts, pid, tasks}` to
`$OP_HEARTBEAT_DIR/<name>.json` on a fixed interval, idle or not
(`src/services/curation/worker_liveness.py`). A dead sub-task fails the check
even when the file is fresh. The compose healthcheck runs:

```bash
python /app/src/services/curation/worker_liveness.py check detection_worker --max-age 120
```

It exits `0` or `1` and prints the reason; the names are `detection_worker` and
`vlm_worker`. Celery workers are checked through their own pool
(`scripts/healthcheck/celery_pool_healthcheck.py <queue>`), the beat by its
schedule file. `unhealthy` in `docker compose ps` means stuck, not idle.
`GET /ready` names a down database, queue or disk; Flower (monitoring profile,
port 4613) shows queues and tasks.

## Pausing

There are two independent pauses, both stored in PostgreSQL so every worker
reads the same state.

- **Per project.** `POST /curation/projects/{project}/pause` makes every
  worker skip that project's work; `POST .../resume` clears it
  and `GET .../pause` reports `paused` and `paused_by`. Other projects keep
  running. A job that is already running yields at its next slice boundary.
- **Global, for the VLM.** The VLM workers idle while the deployment's
  training pause is set. The GPU arbiter sets it before a single-GPU training
  run so the worker doesn't compete with the trainer, and
  `openprocessor vlm use` sets it while it swaps the model. For a multi-GPU
  claim the arbiter stops configured containers instead
  (`OP_GPU_ARBITER_CONTAINERS`, `docker-compose.gpu-arbiter.yml`). Without
  the arbiter overlay the VLM workers are not paused during a run.

## Where job state lives

Job state is never in process memory or on a volume: a job is a PostgreSQL row
(`GET /curation/projects/{project}/jobs`) and its messages travel through Valkey.
Training outputs sit under `OP_TRAIN_RUNS_ROOT`; their status is in `jobs`.

Events are `events` rows announced by a Valkey wake-up, so
`GET /curation/events` sees events from any process (including the detection
worker's `POST .../events/publish`) and resumes with `Last-Event-ID`. A project's
stream delivers only its own events. See [Jobs](jobs.mdx).

## Worker metrics

The detection worker serves its own Prometheus `/metrics` on
`OP_REGION_WORKER_METRICS_PORT`. Stage concurrency is set by
`OP_REGION_WORKER_VLM_CONCURRENCY` and
`OP_REGION_WORKER_VLM_VISIBLE_CONCURRENCY`. The job gauges (`op_jobs{kind,status}`,
`op_jobs_oldest_queued_seconds`, `op_jobs_failed_total`) are in the Prometheus metrics too.
