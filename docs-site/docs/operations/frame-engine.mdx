# The frame engine

The frame engine (service `frame-engine`) is the part of OpenProcessor that reads your photos. It
decodes each photo once on the GPU and, from that one decoded frame, runs the detector, the
embeddings, and when asked the faces and the text. It also cuts the crops. The API never decodes
a photo itself. The engine calls the models in Triton, so it must run on **the same GPU as
Triton**. It starts with the core stack; there is nothing to enable beyond `OP_INGEST_GPU_DECODE`
([below](#settings)).

Speed numbers are on [Measured performance](../reference/performance.mdx).

## What it needs

- **GPU memory** on the Triton card: about 6 GB at the sizes the `full` profile uses, 3.3 GB idle
  there, a few hundred MiB at the smallest sizes (the installer writes the sizes for your card).
  A wide-gamut photo (Display P3, Adobe RGB) adds 48 MiB per profile, at most two profiles.
  See [GPU sizing](../deployment/gpu-sizing.mdx).
- **Host memory:** 2 GB reserved.
- On `minimal`, `small` and `standard` the installer sets `OP_INGEST_GPU_DECODE=0`: the engine
  runs at its smallest sizes and is not called; the API decodes on the host instead.

## Is it healthy

```bash
./openprocessor status      # frame-engine: healthy
./openprocessor gpu plan    # GPU decode on or off, and the engine's share of the card
```

Healthy means Triton answers and the engine's shared-memory region is registered. It is also on
the metrics port (4613, `op_frame_engine_*` series, see [Monitoring](./monitoring.mdx)). After a
Triton restart the engine finds Triton again and registers its region by itself, about 13 seconds
after Triton is back; it does not need a restart.

## What a 503 `engine_unavailable` means

An ingest request answers **503** with `Retry-After` (5 seconds) and `"code": "engine_unavailable"`
when none of its new photos could be given to the engine: it is down, not ready, or overloaded past
its deadline. **Nothing of that request was stored.** Send it again after the `Retry-After`; the
bulk ingest (folder, S3, watched source) does this itself, waits, and does not count it as a failed
attempt. When only some photos of a request meet the engine's trouble, those photos answer
`failed` with the same code and the rest are stored; resend the failed ones. A photo is stored
whole or not at all.

Before a batch the API asks the engine whether it is ready. If the call itself is refused by the
transport (a connection reset, a `GOAWAY`), the probe is asked again on another channel, up to
3 times, 0.1 s and 0.2 s apart and 2 s each; only an answer counts as a verdict. An engine that
refuses connections is judged in about 0.3 s, one that accepts and never answers in at most 6.3 s.
The log tells the two causes of a 503 apart: `ingest_engine_not_ready` (the engine answered "not
ready") and `ingest_engine_probe_undelivered` (it could not be asked; it names the gRPC code), and
`op_engine_probe_total{outcome}` counts `ready`, `recovered`, `not_ready` and `undelivered`
([Monitoring](./monitoring.mdx)).

### A photo whose engine call was lost

The call for one photo is a pure function of the photo and the plan: the engine stores nothing, so
sending it again is safe. The API sends it again, up to 3 times with a short growing pause, when
the engine answers `UNAVAILABLE` or when the transport lost the stream (`INTERNAL` with a text
such as `Stream removed` or `Received RST_STREAM with error code 1`), and for as long as the
photo's 120 s deadline when the engine answers overloaded. An `INTERNAL` that the engine raised
for the photo (its text starts with `frame engine:`) is not sent again: it would fail the same
way, and the photo ends `engine_unavailable` with that text in the API log
(`frame_engine_call_failed`). That line names the gRPC `code`, the number of `attempts`, the
`request_id` and the `pid` of the API process; every API log line carries `pid`, so the other
lines of the same process (a `fork_posix.cc` warning, an ExifTool failure) are one filter away.
`op_engine_call_failures_total{code,outcome}` counts every failed attempt, `retried` or
`exhausted` ([Monitoring](./monitoring.mdx)). See
[gRPC status codes](https://grpc.io/docs/guides/status-codes/).

A file the engine cannot read answers `decode_failed` (not transient, it uses an attempt), and one
larger than `OP_FRAME_ENGINE_MAX_MEGAPIXELS` is refused from its header before any decode.

## Settings

Set these in `.env`, then `./openprocessor restart`. Defaults
suit a `full` card; the installer writes sizes for smaller profiles. The complete list with
comments is in `env.template`.

| Variable | Default | Change it when |
|---|---|---|
| `OP_INGEST_GPU_DECODE` | `1` on `full`, `0` otherwise (installer) | `1` sends every photo through the engine; `0` makes the API decode on the host |
| `FRAME_ENGINE_GPU_ID` | Triton's card | never apart from Triton: they must share a card |
| `FRAME_ENGINE_METRICS_PORT` | `4613` | the port is taken (the `monitoring` profile's Flower also publishes 4613) |
| `OP_FRAME_ENGINE_URL` | `frame-engine:8001` | the engine runs elsewhere |
| `OP_FRAME_ENGINE_WORKERS` | `16` | photos processed at once; lower it on a small card |
| `OP_FRAME_ENGINE_MAX_IN_FLIGHT` | `128` | requests admitted at once; above it the engine answers overload and the API retries |
| `OP_FRAME_ENGINE_BUDGET_MIB` | `2048` | decoded-frame memory; more for many 40 MP photos at once, less on a small card |
| `OP_FRAME_ENGINE_REGION_MIB` | `1024` | the shared-memory region to Triton; a photo with hundreds of detections wants more |
| `OP_FRAME_ENGINE_POOL_MIB` | `4096` | cap of the engine's device-memory pool |
| `OP_FRAME_ENGINE_MAX_MEGAPIXELS` | `100` | you have bigger images (or want a lower refusal limit) |
| `OP_FRAME_ENGINE_MIN_MEGAPIXELS` | `0` | below it a JPEG is decoded on the host; `0` keeps every baseline JPEG on the GPU |
| `OP_FRAME_ENGINE_TRITON_TIMEOUT_SECONDS` | `15` | a model call is cancelled after it |
| `OP_FRAME_ENGINE_REQUEST_DEADLINE_SECONDS` | `60` | keep under the API's 120 s call timeout |
| `OP_FRAME_ENGINE_JPEG_QUALITY` | `90` | quality of the crop JPEGs |
| `OP_FRAME_ENGINE_TRANSPORT` | `cuda` | `body` sends inputs in the request when CUDA shared memory is unavailable (slower) |

A value that is set but malformed or out of range stops the engine at start and the log names it.
The rest (lanes, threads, waits, colour tables, ports, drain and health intervals) keep their
defaults; see `env.template`.

On the API side the ingest has its own limits: `OP_MAX_INGEST_CONCURRENCY` (photos in flight per
request, 16), `OP_INGEST_INFLIGHT_MB`, `OP_INGEST_READ_THREADS`. See
[Advanced configuration](../configuration/advanced.mdx).

### Removed

A removed variable left in `.env` stops `api` and the workers at start (the installer and CLI name
the line to delete).

| Removed | Use instead |
|---|---|
| `GPU_IMAGE_PREP_MODEL` | none: the decode is the `frame-engine` service; the API finds it at `OP_FRAME_ENGINE_URL` |
| `OP_INGEST_GPU_MIN_MEGAPIXELS` | `OP_FRAME_ENGINE_MIN_MEGAPIXELS` (where the engine's nvJPEG route starts) |
| `OP_OPENSEARCH_DATA` | `OP_DATA_DIR` ([Storage](./storage.mdx)) |

## Troubleshooting

| You see | Look at |
|---|---|
| `frame-engine` not healthy, or ingest answers 503 `engine_unavailable` | `./openprocessor logs frame-engine`. A line naming a setting means that value is malformed. No GPU line means the card is not visible to Docker. `./openprocessor status` shows whether Triton is up first: the engine waits for it. |
| Photos or a request fail with `too_many_pings` or `GOAWAY` in the API log | The API's channels to the engine ping every 30 s, idle or not, and the engine's server accepts that (pings without calls, no more often than every 10 s): `frame_engine.front.SERVER_OPTIONS` and `src.clients.frame_engine.ENGINE_CHANNEL_OPTIONS`, kept in step by a test. A line saying `too_many_pings` means the two sides disagree again, for example an engine image older than the API's: update both. ([gRPC keepalive](https://grpc.io/docs/guides/keepalive/)) |
| A photo fails `engine_unavailable` with `INTERNAL: Stream removed` or `frame of size 9 overflows local window` in the API log, and `fork_posix.cc ... Other threads are currently calling into gRPC, skipping fork() handlers` above it | A process of the API called `fork()` while engine calls were in flight; gRPC does not support that ([gRPC Python fork support](https://github.com/grpc/grpc/blob/master/doc/fork_support.md)). The one cause found was ExifTool's start-up (PyExifTool's `preexec_fn`); the API now starts its ExifTool processes at start-up, before it opens any engine channel, and without `preexec_fn`, so a start-up or a replacement never forks. A new `fork_posix.cc` line names a new cause: find the process that forks (`ps -ef --forest` in the API container). The call itself is also sent again, [see above](#a-photo-whose-engine-call-was-lost). |
| The engine does not start (memory) | The card is too small for the sizes: `./openprocessor gpu plan`, lower `OP_FRAME_ENGINE_BUDGET_MIB` and `OP_FRAME_ENGINE_REGION_MIB`, unload models you do not use, or use `OP_LOAD_PROFILE=ingest` ([Ingest load profile](./ingest-load-profile.mdx)). |
| Engine unready after a CUDA error | A lost CUDA context makes it refuse work as retryable, report not ready and exit; Docker restarts it and it is ready within seconds. Repeated restarts: check `nvidia-smi` and the driver. |
| A model failed to load, `/health` or `/ready` names it | The API loads a model by unloading it first, waiting up to 30 seconds until it is no longer ready, then loading it, so that model answers unavailable for a second or two. If it stays unavailable: `./openprocessor logs triton-server` for the reason, then `./openprocessor models repair`. The engine's own models are `pe_image_encoder`, the detector, and (for faces and text) the `uint8` SCRFD, ArcFace and PaddleOCR engines. |
| Ingest is slow | Look in this order: (1) `op_frame_engine_stage_seconds_total` per stage ([Ingest stage timing](./ingest-stage-timing.mdx)); the largest stage is the limit; (2) `op_frame_engine_overloads_total` rising means the card is full: [Ingest load profile](./ingest-load-profile.mdx); (3) the database and search volumes on a spinning disk: [Storage](./storage.mdx); (4) `op_decode_route_total`: many `cpu_*` routes mean photos are not baseline JPEGs (PNG, WebP, progressive) and decode on the host inside the engine. |
| Photos fail `decode_failed` | The file is not an image any decoder reads, or is above the megapixel limit. It is not retried. |
