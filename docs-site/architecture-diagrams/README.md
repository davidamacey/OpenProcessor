# Architecture diagram sources

`specs/*.json` are hand-authored [Archify](https://github.com/tt-a1i/archify) diagram
specifications (architecture, workflow and sequence types) built from real repo evidence:
`docker-compose.yml`, `src/main.py`, `src/routers/`, `src/services/` (including `src/services/projects/` and
`src/services/config_store/`), `src/config/`, `src/clients/`, `models/ocr_pipeline/`, and the
curation workers under `scripts/curation/`.
They are **not** generated by a static-analysis tool; each one describes how the code
actually fits together, verified by reading it.

Rendered output lives in `docs-site/static/architecture/*.html`, is served at
`/architecture/<name>.html`, and is embedded by `docs-site/src/pages/architecture.tsx`
using the tab metadata in `docs-site/src/data/architecture-diagrams.json`.

## Regenerating

Requires the Archify Claude Code skill (MIT license):

```bash
npx skills add tt-a1i/archify -g
```

Then, from the repo root:

```bash
scripts/generate-architecture-diagrams.sh                  # all specs
scripts/generate-architecture-diagrams.sh system-overview   # just one
```

The script validates each spec at `showcase` quality before delivering; a spec that fails
validation is never silently rendered broken.

## Diagrams

| Group     | id                  | Type         | What it shows |
| --------- | ------------------- | ------------ | ------------- |
| System    | `system-overview`   | architecture | Every compose service and profile: clients, yolo-api, Triton, OpenSearch, the job volumes, the multi-project curation workers, segmenter, VLM endpoints, the host CLI, trainer, evaluator, MLflow and monitoring. |
| System    | `backend-modules`   | architecture | `src/main.py`, core and project-scoped curation routers, the core/curation/detection/labeling/training/projects services, the config store, clients, `src/config/`, and the workers that import the services. |
| System    | `data-model`        | architecture | A project's six indexes (items carry `region_boxes`) and its class registry and exports, the global `op_projects` and `op_global_configs` indexes, and the separate visual-search indexes. |
| Workflows | `core-inference`    | workflow     | `/detect`, `/faces`, `/embed` and `/ocr`: CPU preprocessing in the API, TensorRT models in Triton, and the OCR BLS pipeline. |
| Workflows | `curation-pipeline` | workflow     | Project → ingest or import → embed → cluster → VLM → review → reprocess → export → train → bake-off → promote → probe. |
| Workflows | `region-cascade`    | workflow     | Region detector → segmenter leg → OCR text hint → box selection (`max_regions_per_item`) → VLM verify → per-box text, and the terminal statuses. |
| Sequences | `training-promote`  | sequence     | The per-project job-file protocol between the API and trainer, the GPU arbiter, and the gated promote into Triton. |

## Updating a diagram

Treat a stale diagram the same as any other doc: when the code it describes changes, edit the
matching `specs/*.json` and re-run the generator. Do not hand-edit the rendered HTML in
`static/architecture/`; it is a build artifact and will be silently overwritten.
