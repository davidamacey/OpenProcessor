# OpenProcessor v0.4.0

First generic release, following v0.2.0, v0.2.1 and v0.3.0.

OpenProcessor is a backend for computer-vision dataset curation and training,
with a fast inference API underneath. Ingest images, detect and crop regions,
label them with people and a vision-language model (VLM), import and combine
datasets, export, train and promote models. It works for any image domain.
The optional web UI, Cropwright, is a separate frontend for the same API.

## Highlights

**Inference API** (port 4603, `/v1` twin for the core routes), on NVIDIA Triton
with TensorRT engines:
- Object detection (YOLO11 and YOLO26), batches of up to 64 images.
- Face detection, ArcFace embeddings, verify, search and identify.
- MobileCLIP embeddings and visual search over OpenSearch k-NN.
- PP-OCRv5 text detection and recognition.

**Generic, any-domain labeling** (`/curation`, project scoped):
- Isolated projects: own indexes, directories, class registry, settings and
  jobs, enforced at the OpenSearch transport layer. Clone a project, or combine
  up to eight into a new one (class mapping, dedup, holdout handling, preview
  warnings for a mismatched encoder or differing region profiles).
- Config store: versioned, revisioned configuration with activation, rollback
  and optimistic concurrency (`expected_active`). Prompt packs (what the VLM is
  asked) and region profiles (the region stage) are data you create, activate,
  roll back and test on stored crops, with an impact report on activation.
- Multi-box regions: one or many regions per item, each with its own state,
  text, cluster and vector. Per-project keymaps.
- Dataset import (YOLO, COCO, OpenProcessor export) with preview, by-name class
  mapping, undo and resume; unified `/reprocess` (detect, open-vocabulary,
  region, VLM, embed) with a dry run by default.
- Class identity by name everywhere; human labels and the test holdout are never
  overwritten by an automated writer. Review queues, clustering, semantic
  search, export, training jobs, model bake-off and promotion.

**Full-vocabulary detector and ingest policy**
- The stock detector keeps its whole label space (80 COCO classes) and stores
  every detection as an unlabeled proposal; `seed_from_detector` creates registry
  classes from its labels. A per-project ingest policy sets a detect filter
  (classes, confidence, box area, N largest) and the embedding mode: `all`
  (default), `selected` or `lazy`.
- Every item carries `embedding_state` (`embedded`, `failed`, `deferred`,
  `not_selected`; null for older items). An encoder failure is counted, not
  hidden. Embed what you skipped later with the embed-missing reprocess.
- `OP_INGEST_PRIMARY_CLASS_IDS` is retired and ignored; use the detect filter.

**Shared filters and run on selection**
- One item filter on crops, review, text search, stats, clusters, regions and
  `GET .../detections/summary`. Batch exclude, unexclude, label and move, YOLO
  export and pipeline start accept `crop_ids` or a `selection` (filter, limit,
  sample, seed) with `dry_run`.

**SAM 3 full-image open-vocabulary detection**
- A project-level prompt set (config axis `open_vocab`, routes under
  `/open_vocab`) lists text prompts such as "traffic cone"; SAM 3 runs each on
  the whole image and every hit becomes a normal item with `source_prompt`,
  `open_vocab_set`, `open_vocab_revision` and `mask_polygon`. Run it as a
  reprocess scope (dry run with a cost estimate), try one target on one image
  with `POST /open_vocab/test`, or set `run_on_ingest`. A sweeper finishes
  passes a restart left pending (`OP_OPEN_VOCAB_SWEEP_S`, `OP_OPEN_VOCAB_STALE_S`).
  `GET /open_vocab` lists example templates only with `?include_templates=true`.

**Segmenter gating and region-stage pause**
- One segmenter gate (registry rules, optional vision-model yes/no, optional
  hit-rate sampling) shared by the open-vocabulary pass and the crop region stage.
  The region stage can be paused and resumed per project without losing data.

**VLM model selection**
- A deployment-wide registry of OpenAI-compatible endpoints with a local model
  catalog and an `openprocessor vlm` CLI. Each project activates one; remote
  endpoints need an explicit acknowledgement because crops leave the host.

**Install**
- One-line installer with digest-pinned images and checksum-verified assets.

## Storage sizing and measured speed

- About 8 KB per vector on disk (8.4 KB measured for a 1024-d float32 vector
  with OpenSearch derived source on).
- Per item: about 9 to 10 KB with a vector, about 1 KB without one. An image
  document with its whole-image vector is about 8.7 KB; a default-pipeline image
  with 1.3 detections is about 22 KB. Formula and layout rules:
  `docs/opensearch_schema_design.md` and
  `docs/design/storage_sizing_and_ingest_baselines.md`.
- Measured ingest on the public COCO set (2,000-image subset, one run): 13.39
  images/s, 0 failed, 1.37 crops per image. Large 12 to 20 MP JPEGs are slower
  (about 2.5 images/s) because decode and resize dominate. See
  `docs/PERFORMANCE.md`. The full-vocabulary per-1,000-image costs there are
  computed, not measured.

## Compatibility

The `contracts/` directory is the frozen wire contract (OpenAPI and generated
TypeScript types); `scripts/codegen/generate_contracts.py --check` fails when it
drifts from the code. Any frontend, including the optional Cropwright UI (a
separate project), builds against it.

## Upgrade notes

- The `Pre-release 0.1.0` entry in `CHANGELOG.md` is private history that was never
  published. v0.4.0 is a fresh wire against v0.3.0 (see the curation API contract);
  there is no data migration, deployments re-ingest.
- k-NN indexes use OpenSearch derived source. Indexes created by pre-release
  builds with it disabled must be recreated (fresh installs only).
- Previous public releases are v0.2.0, v0.2.1 and v0.3.0. v0.4.0 is the next
  version and is not a drop-in upgrade of v0.3.0 data: the curation wire changed
  and there is no data migration, so re-ingest. `./openprocessor upgrade` backs up
  first.
- Remove `OP_INGEST_PRIMARY_CLASS_IDS` from your `.env`; it is ignored and logged.
- Activation calls: a missing `expected_active` is accepted when nothing is active
  and answers 409 `active_conflict` when something is (the message names the shape).

## Requirements

- Linux, Docker with Compose v2, an NVIDIA GPU (Ampere or newer) with driver 535+
  and the NVIDIA Container Toolkit. The installer never installs packages.
- VRAM: about 16 GB for `core` (6-8 GB cards use `--profile minimal`); the
  `curation`, `segmenter`, `vlm` and `trainer` tiers add to that
  (README, Tiers). 16 GB RAM minimum, 32 GB recommended.
- Disk: about 60 GB for `core`, about 135 GB for every tier (the Triton image
  alone is about 30 GB), plus 20 GB headroom.
- Storage: see "Storage sizing and measured speed" above.

## Release policy

- The `latest` image tag is published together with `0.4.0`, so `latest` is `0.4.0`
  at release. Later stable releases move it with `make release`; the installer
  always uses the digests in `images.lock`, never `latest`.
- `--cpu --control-plane-only` is an optional installer mode, not the default: it
  starts only OpenSearch and the API (plus Cropwright if asked), with no Triton,
  workers, VLM, segmenter or trainer.
- VLM catalog entries other than the `tested` ones
  are marked unverified/experimental and are never selected automatically.
- Documentation: a public GitHub Pages site (built from `docs-site/`) and a local docs
  container (`docker compose -f docker-compose.yml -f docker-compose.docs.yml up -d --build docs`).

## Quick start

```bash
curl -fsSL https://raw.githubusercontent.com/davidamacey/OpenProcessor/main/setup-openprocessor.sh | bash
```

Pin this release with `bash -s -- --version v0.4.0`; add `--dry-run` to see every
command first. To verify the download yourself, fetch `setup-openprocessor.sh` and
`SHA256SUMS` from this release and run `sha256sum --check`
(README, "Verify the download yourself"). Then open
`http://localhost:4603/docs`. Full guide: `INSTALLATION.md`.

## Security notes

- Grafana keeps its default `admin` password. That is acceptable for LAN-only installs.
  **Change it before exposing the stack beyond your LAN.**
- Trivy CRITICAL gate: `CVE-2026-6653` (libxml2, Debian trixie, no fixed version) is
  allowlisted as an owner-accepted item and re-checked every release. So are the
  `linux-libc-dev` kernel-header CVEs (headers only, no kernel runs in a container,
  no upstream fix), each listed with a reason in `scripts/release/trivy-allowlist.txt`.
  The trainer's mlflow 2.x findings remain a known item (#110).

## Known limitations

- Trainer mlflow 2.x CVEs (#110) need a deliberate move to 3.x of client and server
  together.
- Export can run out of memory when Triton and the API share a 12 GB card (#111).
- Clustering is index-wide: it runs over the whole project, not over a filter
  (arbitrary-filter clustering is deferred).
- GPU and Triton inference optimization (decode once, stay on the GPU) is open
  work, #40; the measured speeds above are before it.
- Shard budget: each project is six single-shard indexes, so the number of
  projects a node holds is bounded by its heap (`shard_budget_exceeded`,
  `shard_budget_high`, `OP_SHARDS_PER_HEAP_GB`). The installer sizes the heap to half
  of RAM (2 to 30 GB) and warns when `vm.max_map_count` is too low; see
  `docs-site/docs/deployment/sizing-and-storage.mdx`.
- Images are large (tens of GB for the first pull); slimming is #41.
- 12 GB cards such as the RTX 3080 Ti run the minimal profile; their TensorRT
  engine builds use a smaller workspace and are less tuned (#42).
- The installer installs published releases only; before publication a source
  checkout uses `scripts/setup.sh`.
- Cropwright screenshots in the docs are marked pending (#43).
