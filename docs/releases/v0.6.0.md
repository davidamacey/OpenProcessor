# OpenProcessor v0.6.0

The speed and selective-labeling release. Ingest got measurably faster on public data (images are
decoded once, detector and embedding inputs travel to Triton as uint8, the embedding engine is FP16,
large photos decode on the GPU, the embedding encoder can use several GPUs, writes to OpenSearch are
batched), and the new **assist runs** let you point the VLM at exactly the crops, boxes, clusters or
filters you choose. Bulk ingest from a folder, a manifest or S3 runs in the background with a preview
first. The codebase was also cleaned up (guards, dead code removed, large files split, one typed env
module, one docs site as the single source of truth). Cropwright follows the monorepo version, 0.6.0.
Everything in v0.5.0 is unchanged in kind; the behaviour changes come first under Upgrade notes.

## Highlights

**Assist runs (selective VLM and segmenter work)**
- `POST /assist/runs` (dry run by default) sends a crop, a selection, a cluster, a sub-cluster or an
  item filter to the VLM, whole or as a seeded representative sample, with `classify`, `attributes`,
  `verify` and `segment` actions. Class answers go through the guarded writer, so a locked, validated
  or holdout item keeps its class; every answer is stored in the item's `assist` object.
- Cluster and sub-cluster label proposals carry the agreement and vote distribution, and an explicit,
  dry-run-first apply refuses a changed scope (`409 scope_changed`).
- Prompt packs declare `attributes` (item or box facts) instead of the old hard-coded `make` and
  `model`. Cropwright gets an **Assist...** dialog on the cluster page, a crop, and a box.
- A project calls no VLM until it activates one.

**Ingest**
- Bulk ingest of a folder, manifest or S3 and S3-compatible store as a background run, with a
  preview (`/ingest/bulk/preview`), registered sources, poll, cron and webhook triggers, and a
  Cropwright panel. Detection-only ingest (`embedding.mode: "none"`, `clustering.automatic: false`).
- Measured speed-ups on public data (set A is the pinned 2,000-image COCO set, set B the pinned
  12 to 24 MP photos; method, caveats and raw JSON are in `docs/PERFORMANCE.md`):

| Result | Before | After |
|---|---|---|
| PE image encoder engine, per embedding (FP16) | 13.7 ms | 5.5 ms |
| Ingest through `/ingest/upload`, set A, one card (FP16 engine) | 8.9 images/s | 17.4 images/s |
| Request bytes to Triton per image, set A (uint8 inputs) | 14.94 MB | 3.73 MB |
| API CPU per image, set A (uint8 inputs) | 0.118 CPU-s | 0.062 CPU-s |
| Photo ingest, 8 / 16 / 32 / 64 clients (pixel work off the event loop) | 5.2 / 8.7 / 10.8 / 4.9 images/s | 21.5 / 27.3 / 23.6 / 24.1 images/s |
| Ingest, set A, one A6000, tuned detector engine and concurrency | 23.39 images/s | 28.81 to 29.07 images/s |
| Ingest, set A, two A6000 (data-parallel PE encoding) | 23.39 images/s (one card) | 44.60 images/s (1.91x); tuned 55.08 to 56.37 |
| Photos (set B) ingest, detect + embed (GPU decode) | 27.0 images/s | 35.0 images/s |
| Host CPU per photo at bulk (GPU decode) | 1.12 CPU-s | 0.34 CPU-s |
| Cluster pass plus geometry stage, 10,000 crop vectors | 176.4 s | 24.9 s |
| Cluster pass, 100,000 vectors | 310.6 s | 138.0 s |
| OpenSearch write ceiling, 100,000 real vectors | 473 documents/s (1 writer) | 1,980 (4 writers); 4,426 (8 writers) |
| Vector index size per item (faiss to Lucene engine, new projects) | 8.6 KiB | 4.5 KiB |

- Measured and not adopted: INT8 for the PE encoder (faster, fails the accuracy gates), system shared
  memory between the API and Triton (under 5 percent of API CPU), a gRPC ingest channel.

- Scale ladder (one RTX A6000, VLM off, OpenSearch and sources on a NAS; `docs/PERFORMANCE.md`, "Scale ladder: 10k and 100k"):

| Run | Throughput | Share of the 2k baseline (29.0 images/s) | Wall | Failures | Crops | Cluster pass | Index |
|---|---|---|---|---|---|---|---|
| 10,000 public COCO images | 29.04 to 29.08 images/s | 100 % | 311 s | 0 | 64,415 | 269 s | not measured |
| 100,000 public Open Images v7 (CC BY 2.0, up to 0.7 MP) | 35.96 images/s | 124 % | 2,781 s | 2 (fixed, #333) | 490,804 | 2,042 s | 8.86 GiB |
| 100,000 private 20 MP camera-original JPEGs (aggregates only, not redistributable) | 21.00 images/s | 72 % | 4,761 s | 0 | 236,689 | 1,802 s | 4.35 GiB |

  Each run was stopped by force part-way and resumed with no lost or repeated image. Throughput does not
  decay over 100,000 images on the small-image set. The small-image runs are bound by GPU embedding; the 20 MP
  run leaves the GPU about half idle, so its limit is upstream of the card (file reads, decode, byte
  budget), which is v0.7.0 work (#40).

**Repository and operations**
- Guards in pre-commit (file size, layering, complexity, broad excepts, unused code, cited paths,
  mypy with untyped defs refused), digest-pinned base images, environment variables read through one
  typed module, and the large source files split by concern.
- The documentation site is the single source of truth for user and operator docs; a script checks
  docs against the code (routes, `OP_*` variables, CLI commands, make targets, links).
- New monitoring alerts (Triton model not ready and others, #290), a git-ignored
  `docker-compose.local.yml` overlay, `./openprocessor curation up [service...]`, and
  `./openprocessor profile` that sets the GPU decode flag.
- Large camera photos: the bulk-ingest admission gate and serial file reads held a 20 MP workload at 21 img/s; after the fixes a 20k slice ran at 27.2 img/s (94% of the 2k baseline). See `docs/design/ingest_write_path_investigation.md`.

## Upgrade notes / behaviour changes

Read these before upgrading from 0.5.0.

Read these before upgrading from 0.5.0.

- **New projects start with the VLM off** (#282). A project calls no VLM until it activates one (`GET .../vlm/endpoints/active` answers `source: "off"`). Projects that exist already are pinned once, at the first start of this version, to what they had (`env` when `OP_VLM_URL` was set, else `off`), so their behaviour does not change.
- **`make` and `model` are no longer hard-coded VLM outputs.** The reply keys, `vlm_item_make` and `vlm_item_model` are gone (old values stay in old documents, unread). Declare such facts as prompt-pack `attributes`; assist runs store them in the item's `assist` object.
- **The VLM routes `label_cluster` (per cluster) and `verify_regions` are removed.** Use `POST /assist/runs` (a `cluster` target, or `verify` on a `crops` or `boxes` target), or `?cluster_id=` on `auto_label/start`.
- **`curation-evaluator` moved from the `curation` profile to its own `evaluator` profile**, so `--profile curation up -d` no longer reserves a GPU for it. Start it with `./openprocessor curation up curation-evaluator`.
- **`CROPWRIGHT_*` env names are now `OP_CROPWRIGHT_*`** (`_IMAGE`, `_BIND_ADDRESS`, `_PORT`, `_INGEST_MAX_REQUEST_MB`, `_DATASET_UPLOAD_MAX_MB`). A `.env` that still sets an old name is refused at startup (`./openprocessor` and the installer exit 2, the container exits). Rename the keys and run `./openprocessor restart`.
- **Region-profile fields `aspect_min` and `aspect_max` are retired** (and the matching aspect min and max region-detection variables). A stored profile that carries either is rejected by name, and skipped with a warning when the registry loads; re-save it without them.
- **Rebuild the detector and PE image encoder engines** (`./openprocessor models repair`): both now take uint8 input, and a model whose plan and `config.pbtxt` disagree does not reach READY.
- **GPU decode is on by default** for the `full` profile (`OP_INGEST_GPU_DECODE`; `minimal` and `standard` default off). It adds about 8.5 GB to the Triton card.
- **New projects use the Lucene vector engine** (`ef_construction` 128); existing projects keep their faiss fields (no migration; re-ingest to move one).
- **Tests default `OPENSEARCH_URL` to a refused local address**, so an offline test run never reaches a live OpenSearch; set `OPENSEARCH_URL` for the live suite.
- **Retired region statuses `pending` and `pending_verify`, `regions.by_human` (use `regions.by_human_drew`) and `scripts/curation/region_worker_main.py` are removed.** `scripts/curation/ingest_walker.py` is replaced by `scripts/curation/bulk_ingest.py` (`--folder` instead of the old flags).
- **`TRITON_WORKERS`, `MAX_BATCH_SIZE` and `SHM_SIZE` are gone** from `.env`, `env.template` and the profile JSON (nothing read them); `setup.sh` no longer writes `docker-compose.override.yml`.
- **New environment variables** (all optional, documented in `env.template`): `OP_ASSIST_JOBS_DIR`, `OP_BULK_INGEST_DIR`, `OP_API_LOOPBACK_URL`, `OP_CPU_POOL_THREADS`, `OP_INGEST_INFLIGHT_MB`, `OP_INGEST_GPU_DECODE`, `OP_INGEST_GPU_MIN_MEGAPIXELS`, `OP_INGEST_DISPATCH_S`, `OP_CLUSTER_REFRESH_INTERVAL_S`, `_GROWTH_THRESHOLD`, `_MAX_DEFERRAL_S`, `_RETRY_BACKOFF_S` and `_AUTO_LABEL`, `OP_S3_ALLOWED`, `OP_S3_ENDPOINT_URL`, `OP_S3_REGION`, `OP_S3_PATH_STYLE`, `OP_S3_FETCH_WORKERS`, `OP_S3_LIST_WORKERS`, `OP_S3_INFLIGHT_MB`, `OP_S3_MAX_OBJECT_MB`, `OP_SOURCE_ROOT_HOST`, `OP_VLM_POLL_S`, `OP_VLM_WAIT_S`, plus the renamed `OP_CROPWRIGHT_*` set. `OP_HNSW_EF_CONSTRUCTION` now documents the new default of 128.
- **Compose changes**: the `evaluator` profile above; Triton gets `CUDA_DEVICE_ORDER=PCI_BUS_ID` (so `TRITON_GPU_ID=0,2` means the lowest listed id first), `CUPY_CACHE_DIR` and glibc malloc tuning for the API; Triton runs with `--log-verbose=0`; the API's memory reservation uses the `deploy.resources.reservations` form; an optional git-ignored `docker-compose.local.yml` is loaded after the stock files; the `gateway-wrap` message names `OP_CROPWRIGHT_BIND_ADDRESS`. Image defaults now point at `0.6.0`.

Upgrade with `./openprocessor upgrade` (or `./setup-openprocessor.sh --version v0.6.0`); it backs up
first and `--rollback` restores the newest backup. Then run `./openprocessor models repair` to rebuild
the uint8 detector and PE engines, and hard-refresh the browser after upgrading. Cropwright 0.6.0
requires backend 0.6.0.

## Requirements

Unchanged from 0.5.0: Linux, Docker with Compose v2, an NVIDIA GPU (Ampere or newer) with driver 535+
and the NVIDIA Container Toolkit; about 16 GB VRAM for `core` (6 to 8 GB cards use `--profile
minimal`); 16 GB RAM minimum; about 60 GB disk for `core`; `vm.max_map_count` of at least 262144.
The GPU decode adds about 8.5 GB to the Triton card, so it is on by default only for the `full`
profile.

```bash
curl -fsSL https://raw.githubusercontent.com/davidamacey/OpenProcessor/main/setup-openprocessor.sh | bash
```

Then open `http://localhost:4603/docs`. Full guide: `INSTALLATION.md`.

## Known limitations

- **The zero-copy GPU pipeline and the 1M-image scale step are v0.7.0.** 0.6.0 decodes once and
  decodes large photos on the GPU, but does not keep a decoded frame resident across every model.
  The v0.7.0 milestone:
  - #40 Triton inference pipeline optimization (decode once, stay on GPU)
  - #41 slim the container images
  - #42 smaller-GPU (12 GB) TensorRT engine builds
  - #67 request-driven processing plans
  - #84 car-wheel teacher-student loop on public COCO
  - #219 work crops at model size for the VLM and region consumers
  - #220 faces and OCR on resident crops
  - #231 ortloom-serve against Triton on the ingest-path models
  - #268 stage 2 follow-ups (set B photos, minimal and standard profiles, two-card instance sweep)
  - #286 iterative cluster-sampled VLM auto-labeling
- **The API has no authentication.** Do not expose it; see `SECURITY.md`. Prometheus and MLflow have
  no authentication either, and Grafana keeps the default `admin` password on LAN-only installs.
- Existing projects keep their faiss vector fields; only new projects use the Lucene engine.
- #259: the embed reprocess pass stops at about 58 percent GPU and its crop vectors differ slightly
  from ingest vectors (cosine minimum 0.9855).
- Open follow-ups: #101 (pin the VLM connection to the validated IP), #154 (the trainer still uses
  deprecated MLflow registry stages), #155 (SvelteKit `config.alias` deprecation).
- The documentation screenshots may predate the newest UI changes.
